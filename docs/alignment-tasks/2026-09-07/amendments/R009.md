# R009 — 资源前 schema 候选与晚到 observation demand

T06 接线时确认：T31 在资源前缓存 schema/source/transport，但 C03 的 ObservationDemand 由 AttachRun 返回，只有资源阶段才可得知。不能同时声称最终 transport 已在所有资源前选定且随后按 demand 改选。R009 明确同一 resolved invocation 的分段解析，不复制执行管线。

1. 资源前仅一次 NormalizeOutputSchema，并按 T31 的原 policy/HITL/source 规则预验证真实可用候选，候选各自 source 固定。schema 非法或所有候选不可行仍在资源前失败，保留现有 typed error 与 nil/精确矩阵语义。
2. 保留原 providerRichTransport 的初选。只在该驱动既有 rich 能力真实可用时增加可行 batch 候选；不能从零 StreamCapability 推测 rich，也不新增 transport-lock SPI。遵守配置捕获后的 StreamSupport/StreamCapability，未证明的构造配置不靠猜测覆盖。
3. AttachRun 后 OR 合并需求，只对已验证候选按 C03 的 Skills/MCP/Subagents/Todos 四位评分，平分保留原选择，无需求行为不变。最终选择一次写入 resolved request；不再次 normalize/schema编译、物化、解析resolver或改policy。每候选 source 已冻结，选择前不追加prompt schema指令。
4. 观测引入的切换不得消音原须保留的 Ask，包括无 schema 的显式 Ask（nil schema resolver直接成功不可绕过）。这个约束不全局拒绝原本初选batch且通过自身合同支持Ask的第三方驱动。精确矩阵的适用Ask含默认值；nil保留原显式边界。
5. 已请求的观察在所有可行候选中不可用时，按 C03 发一次安全 observation_unavailable Notice 后运行，不造空快照或业务失败。Run/Stream、无demand、无schema与Ask、矩阵nil/精确、初始batch Ask均需对照fixture。

同批 T07 的默认值裁决也明确：schema eligibility 用 R005 的有效默认Ask；Claude interactive 仍按 C04冻结的 wantsInteractiveClaude(raw policy) 启动。零raw policy schema可转prompt并校验，但保留observational，不偷偷AutoApprove，也不把它当已发生Permission往返。真实继承Permission使用QuestionAsk+Permission unset触发已支持的双向transport并实际应答；无schema默认行为保持。若真实协议/现有合同出现反例，带证据重新打开，不能静默全局换默认值。
