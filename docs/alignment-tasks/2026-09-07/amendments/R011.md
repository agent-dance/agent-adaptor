# R011 — G02 常驻复用回归与兼容维度纠正

G02 固定675485d906acabd896c6c0d76e6b13fa09713a87全仓失败：Codex WithTools 期望1次启动实际2；CodeBuddy warm→native schema→after 期望3实际4。原G01两例通过。诊断用只读日志证明两条独立原因，未修改原测试期望。

1. MCP writer 原来将已有 config.toml 的0600改为0644，真实mode已入最终快照后触发Thread重绑。JSON/TOML资源writer必须保留现有regular文件mode，新文件沿用既有0644默认；非regular或IO错误显式失败。保留真实文件mode参与快照、未知内容及ownership证明，不能把全部mode规范化掉。不能扩大任意路径读写/删除，不能把用户更改的权限忽略。
2. C03要求“所选transport参与Thread fingerprint”过强。Request.Streaming是每轮交付选择，不是第二会话身份。移除该独立布尔哈希项，保留所有原有Driver构造配置及codec/version、模型/identity、resolved workspace、catalog/profile/Tools/skills/instructions/MCP/runtime维度。真实transport如改变checkpoint编码或会话环境，仍须由既有SessionConfigFingerprinter、SessionCodec参数及Driver启动前guard稳定表达并拒绝不兼容，不能一概忽略。每轮真实argv/env/机制仍由Driver eligibility/私有启动signature检查。
3. 对正式支持跨transport续接的同一已配置Driver/codec，兼容的rich→临时schema batch→rich不得仅因Streaming不同重绑Thread。临时轮停止旧writer、成功后使用同一健康checkpoint构建后续resident spec；WithSpawn不注册writer，交付后不自动重放。保持原3次启动断言，并核对同一内部active记录/正式resume、每prompt一次、预热实际复用；ResumeOnly跨兼容transport可用，实际配置/profile变化仍拒绝或安全重绑。

归属仍为T06原allow，无生产scope/依赖/任务数/要求ID变化。T06 attempt3新增AC07和V04（完整codex/codebuddy包），原V01/V02/V03继续在最终SHA执行。固定G02反例作为回归，T20/T22独立验证，T10不得重新引入Streaming身份维度。原T06 attempt2、G02 attempt1和所有失败证据保留；G02须重验合流新SHA后才能派发B03。G02集中docs与C03/C04同步，不能只删代码而保留错误合同。此修订不提供原生平台或live验收。

同一修订实施期的平台说明：本地Go1.26.5 `os/types_windows.go` 中readonly的Stat权限为0444、writable为0666，Chmod仅有0200可观察语义。新增fixture必须保留POSIX精确断言，并比较平台真实观察值；Windows的0600→0640不是可观测变化，不得据此断言漂移。Readonly原子替换若OS拒绝，必须保持原权限/内容并显式返回错误，不放宽只读/ACL。缺失MCP文件用于快照的合成默认也采用平台真实观察表示（Windows0666，POSIX0644）；这只是确定的fingerprint输入，新文件writer仍调用既有0644，既有实物始终按Stat实际mode，不实际chmod到0666，不削弱ACL。纯平台映射测试不算原生Windows证据。
