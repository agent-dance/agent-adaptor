# R007：profile释放点及Windows长期锁句柄

修订8，来自C01对T04当前实现的独立只读审阅。96要求/42任务/7批次不变；T04-AC03新增明确验收，T20/T26独立验证。

1. P1：原ReleaseClean先unlock再Close，最后才released=true；解锁后Close失败，下次会重新写ready及unlock已关闭/nil句柄，可能破坏B已接管的active状态。修正逐阶段记账，成功unlock之后永不重写state或重新获取所有权，只重试尚需清理的资源。
2. C01 §5/§8的“任何Close错误都仍持锁/B被拒绝”限定为成功unlock之前。unlock为不可逆的释放点；此时writer/gateway/prune与ready持久化均已完成，B可安全接管。之后的句柄清理错误仍可观察，旧Agent仍拒绝新运行，但不能假称继续持锁。不得重试已关闭fd导致EBADF、nil panic或关闭复用fd。
3. Windows os.Root.OpenFile在当前Go stdlib使用FILE_SHARE_DELETE，不能提供冻结的长期no-share-delete保证。owner.lock需专用长期CreateFile句柄、不共享delete并核对file ID/reparse/hardlink及目录身份；临时ACL校验句柄不构成持锁期间保护。新增Windows持锁rename/delete必须失败的fixture；Darwin交叉编译不能作为原生Windows通过。

T04需验证A成功unlock后Close失败、B获取并写active、A重试时B的generation/锁/状态逐字不变。此精确边界覆盖原C01不可实现的全错误保锁表述，不放松释放前单writer、权限、cleanup与token撤销要求。
