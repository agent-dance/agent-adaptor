# agent-adaptor v0.5.0 — Host Integration Plan

> 本版是经过多轮架构评审后定稿的 v0.5.0 计划。每一项设计都经过对 `AGENTS.md` §1 / §2 / §7 / §8 红线的反复对照，并沉淀出 11 条通用设计判据（§0.2）作为本期及后续 minor 版本的设计标尺。

主题一句话：**把生产宿主用 v0.4.0 跑过一轮后必写的"标配代码"沉淀到 SDK；纯 SDK 定位 + 单一职责一寸不让**。

> 起源：基于 `agent-registry`（容器化、多任务并发、HITL 持久化、远端 skill catalogue、双通道产物上报）这种典型生产宿主用 v0.4.0 跑了一轮后给出的反馈。每一条改进都是真实痛点驱动，不是设计美化。

## 0. 设计前提

### 0.1 守住 AGENTS.md 红线

| 红线 | 本计划如何守住 |
|---|---|
| §1 纯 SDK，不引入 server / 队列 / 调度器 / auto routing | 全部改进都是注入点扩展、source 类型新增、hosttools 文档化 + 纯函数 helper；不引入任何新的执行入口、不内置任何服务化能力 |
| §2.1 只有一套执行语义 | 不新增 Run / Start 同级方法。所有改进都收敛在已有 `resolveInvocation` 之前或之后的钩子上 |
| §2.2 默认 Agent 绑定优先 | 不动 binding 模型，不动 `WithDefaultAgent` / `WithAgent(name, ...)` 入口 |
| §2.3 无状态默认，状态化可选 | 新增的注入点全部"零值不挂 = 与 v0.4 行为一致"，不强制宿主使用 |
| §2.4 依赖局部化 | 不引入新顶层依赖；所有 archive / http 行为只用 stdlib + 已 indirect 的 `golang.org/x/sync` |
| §7 adapter / helper / hosttool 三层职责边界 | core 接口只做最小补丁；hosttool 改动收敛在 `pkg/hosttools/sessionrecorder` 一个包内，且**不引入新的存储维度** |

### 0.2 通用设计判据

本期评审沉淀的 11 条判据。后续 minor 版本设计先对照判据再做决定：

| # | 判据 | 反例（本期纠正过的） |
|---|---|---|
| 1 | **拆接口的合法理由是"数据流正交"，不是"语义不同"。** Resolve 和 Required 在数据流上都是"宿主返回 Skill 给 SDK"，只是触发原因不同；触发原因是宿主的实现细节，不该上升为接口。 | 早期想拆 `SkillRequiredLister` 独立接口 |
| 2 | **"分两次调用"和"分两个接口"是不同的事。** 宿主商店内部可能两次 RPC（fetch + required），但这是宿主自由决定的实现策略，SDK 接口不该把它固化。 | 同上 |
| 3 | **N 个窄 option（编译期类型保证）> 1 个 option 接受 `any` union（运行时探测）。** 当 SDK 想接受"多种 capability 的任意组合"时，N 个 capability injection 函数比单 option 接 union 类型更安全、更自文档。 | 早期想做 `WithSkillProvider(p any)` |
| 4 | **当一个抽象类型的字段被砍光后，立刻砍这个类型本身。** "未来可能要加字段所以保留 wrapper struct" 是过度封装，违反 YAGNI。已经允许 break 的版本里这个借口尤其站不住。 | `SkillContext{Agent, Prompt, Metadata}` 砍光后保留 `SkillContext{Agent}` 单字段 wrapper |
| 5 | **SDK 接口里出现 Prompt / RunPolicy / Workspace 等"运行时上下文"字段时，停下来问：SDK 是不是想用这个字段做 routing 决策？** 如果"不是，宿主会自己读"——那字段不该出现（宿主已经持有，不需要 SDK 转发）；如果"会"——违反 §2.2。 | 早期想给 SkillContext 加 Prompt 字段 |
| 6 | **透传现有"杂物间"类型给新接口，是接口设计的偷懒。** 当一个已存在的类型混合多类语义（identity / scope / config / tags），新接口要从中精确摘取真正需要的字段定义新类型，不要图省事透传整个杂物间。 | 早期想把整个 `AgentIdentity` 透传给 `SkillResolver` |
| 7 | **当一个抽象只能容纳一种部署模型时，把它写进接口签名等于把该模型钦定为一等公民。** 真实部署模型是多元的（公共 / 单租户 / 多租户 / 联邦 / 实验组），任何"模型特定字段集"在签名里出现都会让别的模型尴尬。 | 早期想引入 `SkillScope{TenantID, ProfileID}` 入参 |
| 8 | **ctx 用法的合法 vs anti-pattern：** anti-pattern 是宿主与 SDK 双方未文档化、靠约定 key 互相塞取；合法 pattern 是 SDK 显式塞、提供公开 helper 让宿主显式取（gRPC metadata / `http.Request.Context()` / OTel 同款）。区分点是 ctx 上的载荷和 helper 是不是 **SDK 公共 API 的一部分**。 | 我前几轮一棒子打死过 ctx 用法 |
| 9 | **分裂"杂物动词"的最好办法不是换签名，而是按它实际承担的子职责拆动词。** v0.4 `SkillProvider.List` 同时承担"按 key 解析"+"列全集"，任何换签名的演进都解决不了根本问题（其中一件事根本不需要列全集）。 | v0.4 `List(ctx, tenantID)` |
| 10 | **在已建立的命名共识上演进语义，优于为新设计创造新命名。** v0.4 已有 `SkillProvider`，宿主已经熟悉。重定义动词（`List → GetSkills`）比换名字（`SkillProvider → SkillResolver`）更优雅，避免概念噪音。 | 早期想引入 `SkillResolver` 新命名 |
| 11 | **可选 capability 优先用 super interface 表达，让 SDK 用 type assertion 探测；不要让宿主在多个 option 之间选择"我注册了哪个 capability"。** `io.Reader` / `io.ReadCloser` 是这个 pattern 的标准范例。 | 早期想做 `WithSkillResolver` + `WithSkillEnumerator` 两个 option |
| 12 | **SDK 内置 source 类型应按"内容载体形态"分类，不按"获取方式"分类。** 载体形态有限（目录 / fs.FS / 字符串 / archive 流 / 自定义）；获取方式无限（HTTP GET / POST / S3 / git / 商店私有 RPC / 内存 / 文件…）。用 reader factory 把"获取方式"折叠到一个函数签名里，让内置 source 集合保持有限封闭。 | 早期想做 `SkillFromURL` 独立类型 |

### 0.3 明确的非目标（即便宿主反馈强烈也不做）

1. 不在 core SDK 内置 ThreadHistoryStore 抽象（thread / conversation 是宿主 ontology，不是 SDK ontology — 详见 §C2）
2. 不让 `RuntimeServiceManager` 长出 `Reconcile / List` 等暗示"SDK 帮我管 lifecycle"的 API（详见 §A3）
3. 不让 `sessionrecorder` 长出"pending / hitl / question 状态"等新的存储维度 — 改用纯函数 derive（详见 §B1）
4. 不在 hosttools 包内造小框架（fan-out `Sink` / `Pump` 抽象）— 让宿主写 8 行 for 循环（详见 §B1）
5. 不引入聚合谓词（`IsExpired` / `IsConflict`）— 它们是单向语义压缩，会锁死未来细化空间（详见 §A4）
6. 不为 `SkillProvider` 引入"全集枚举"必备语义 — 商店模型不能枚举是合法状态（详见 §A1）

## 2. 改进详细设计

### A1. `SkillProvider` 接口重设计

#### A1.1 动机

v0.4.0：

```go
type SkillProvider interface {
    List(ctx context.Context, tenantID string) ([]Skill, error)
}
```

`List` 这个动词同时承担两件事：

| 用途 | 调用点 |
|---|---|
| (a) **按 key 解析**：用户写 `WithSkills(SkillKey("foo"))`，SDK 列全集 → 找 "foo" → 返回对应 Skill | 每次 Run |
| (b) **列全集**：`Admin.ListSkills` 列出可选 catalogue | Admin UI |

这是商店模型不可用的根因。商店宿主真实场景：

- 上万 skill 不可枚举 → (a) 强行触发 List 性能崩
- 用户通过 UI 主动选 → 实际只需要 (a) 按 key 解析
- v0.4 强迫商店宿主返回 `ErrSkillsNotEnumerable` —— 这是 **用 error 表达"我不支持这个能力"** 的反模式

判据 9：分裂"杂物动词"的最好办法不是换签名，而是按子职责拆动词。

#### A1.2 改动

##### A1.2.1 `SkillProvider` 重定义动词为按 key 提供

```go
// SkillProvider is the host-side hook that backs WithSkills /
// WithDefaultSkills. SDK consolidates and deduplicates the SkillKeys
// referenced by one Run, then asks the provider to produce a Skill
// description for each key.
//
// Implementations MAY return additional Skill values not in keys (for
// example tenant-mandatory skills); SDK adds every returned Skill to
// the run's selected set, treating provider-injected additions
// equivalently to user-referenced keys. Keys absent from the returned
// map surface as ErrSkillNotFound.
//
// SDK invokes GetSkills on every Run regardless of whether the caller
// referenced any keys, so provider-injected mandatory skills work even
// when the user passed neither WithSkills nor WithDefaultSkills.
type SkillProvider interface {
    GetSkills(ctx context.Context, keys []string) (map[string]Skill, error)
}
```

判据 10：保留 `SkillProvider` 名字，演进动词，避免心智噪音。

##### A1.2.2 `SkillCatalog` super interface（可选 capability）

```go
// SkillCatalog extends SkillProvider with the ability to enumerate the
// full visible catalogue. SDK uses Catalogue() only for
// Admin.ListSkills; Run-time selection still goes through GetSkills.
//
// Hosts whose catalogue is too large to enumerate (e.g. remote skill
// stores) implement SkillProvider only and skip SkillCatalog. SDK
// reports SkillSyncUnsupported on Admin.ListSkills in that case.
type SkillCatalog interface {
    SkillProvider
    Catalogue(ctx context.Context) ([]Skill, error)
}
```

判据 11：可选 capability 用 super interface 表达，SDK 内部 type assertion 探测，与 `io.Reader` / `io.ReadCloser` 同 pattern。

##### A1.2.3 单一 option

```go
func WithSkillProvider(p SkillProvider) Option
```

宿主传同时实现 `SkillCatalog` 的对象时，SDK 在 Admin 路径自动激活 `Catalogue()`：

```go
// SDK 内部
if cat, ok := s.skillProvider.(SkillCatalog); ok {
    return cat.Catalogue(ctx)
}
return nil, SkillSyncUnsupported
```

判据 3：单一注入入口 + type assertion 探测多 capability —— 不引入 `any`、不要求宿主在多 option 间分配能力。

##### A1.2.4 `SkillSource` 改为公开 marker

```go
// 旧（v0.4，封闭 sum-type）：
type SkillSource interface {
    isSkillSource()  // 第三方包无法实现
}

// 新（v0.5，开放 marker）：
type SkillSource interface {
    SkillSource()    // 第三方可实现
}
```

宿主可以定义自己的 source 类型并配自定义 `SkillMaterializer` 处理。SDK 内置 source 类型（`SkillFromPath` / `SkillFromFS` / `SkillFromInline` / `SkillFromArchive`）同步切换到新 marker。

判据 12：`SkillSource` 应按"内容载体形态"分类、保持有限封闭；获取方式的无限性通过 reader factory（见 §A2）折叠。

##### A1.2.5 暴露默认 materializer 让宿主自定义实现 chain

```go
type DefaultMaterializerOption func(*defaultMaterializerConfig)

func WithMaxArchiveSize(bytes int64) DefaultMaterializerOption
func WithMaxArchiveEntries(n int) DefaultMaterializerOption
func WithSkillCacheRoot(path string) DefaultMaterializerOption  // 默认 $XDG_CACHE_HOME/agent-adaptor/skills

// NewDefaultSkillMaterializer returns SDK 's built-in materializer
// handling SkillFromPath / SkillFromFS / SkillFromInline / SkillFromArchive.
// Custom materializers compose chain-of-responsibility:
//
//     m := &MyMaterializer{Default: sdk.NewDefaultSkillMaterializer()}
func NewDefaultSkillMaterializer(opts ...DefaultMaterializerOption) SkillMaterializer
```

宿主自定义 materializer 模式：

```go
type StoreMaterializer struct {
    Default sdk.SkillMaterializer
    Store   *MyStoreClient
}

func (m *StoreMaterializer) Materialize(ctx context.Context, s sdk.Skill) (string, error) {
    if src, ok := s.Source.(GitPackSource); ok {
        return m.Store.FetchGitPack(ctx, src.RepoID, src.Ref)
    }
    return m.Default.Materialize(ctx, s)  // 内置 source 走 SDK 默认实现
}
```

##### A1.2.6 caller identity 通过 ctx 暴露（gRPC / OTel 模式）

```go
// SDK 在调用 GetSkills / Catalogue 之前把 caller identity 注入到 ctx
// 提供公开 helper 供宿主按需取

// CallerIdentityFromContext returns the AgentIdentity SDK injected into
// ctx before invoking SkillProvider hooks. Implementations that don't
// need caller scoping (e.g. public stores) can ignore this helper.
func CallerIdentityFromContext(ctx context.Context) (AgentIdentity, bool)

// WithCallerIdentity is exported so adapters / middleware that compose
// providers can propagate identity properly. Most hosts don't call it.
func WithCallerIdentity(ctx context.Context, id AgentIdentity) context.Context
```

判据 7 + 判据 8：

- 不在接口签名引入"模型特定字段集"（`SkillScope` / `tenantID string` 都被砍）
- ctx + 公开 helper 是合法的 Go idiom（gRPC metadata / `http.Request.Context()` / OTel `SpanFromContext`）
- 公共商店宿主完全无视 ctx；多租户商店通过 helper 显式取 —— 各得其所

##### A1.2.7 内置 helper 集合

```go
// SkillSet implements SkillCatalog for static in-memory catalogues.
type SkillSet map[string]Skill

func (s SkillSet) GetSkills(ctx context.Context, keys []string) (map[string]Skill, error)
func (s SkillSet) Catalogue(ctx context.Context) ([]Skill, error)

// LocalSkillsFromDir scans root and produces one Skill per subdirectory
// containing SKILL.md. Useful for "everything in /opt/skills/" semantics;
// the result feeds WithSkills / WithDefaultSkills.
func LocalSkillsFromDir(root string, opts ...DirScanOption) ([]Skill, error)

type DirScanOption func(*dirScanConfig)
func WithDirSkillKeyPrefix(prefix string) DirScanOption
func WithDirIgnore(globs ...string) DirScanOption

// SkillsAsRefs converts []Skill into []SkillRef for variadic options.
func SkillsAsRefs(skills []Skill) []SkillRef
```

#### A1.3 宿主使用对照（5 个真实场景验证）

##### S1：静态小 catalogue（v0.4 等价）

```go
catalog := sdk.SkillSet{
    "code-review": {Key: "code-review", Source: sdk.SkillFromPath{Path: "..."}},
    "lint":        {Key: "lint", Source: sdk.SkillFromPath{Path: "..."}, Required: true},
}

sdk.New(
    sdk.WithDefaultAgent(...),
    sdk.WithSkillProvider(catalog),
)
```

`SkillSet` 同时实现 `SkillCatalog`，`Admin.ListSkills` 自动可用。

##### S2：公共商店

```go
type PublicStore struct{ API *PublicAPIClient }

func (p *PublicStore) GetSkills(ctx context.Context, keys []string) (map[string]sdk.Skill, error) {
    return p.API.BatchGet(ctx, keys)  // 不读 ctx；公共商店无 tenant 概念
}

sdk.New(
    sdk.WithDefaultAgent(...),
    sdk.WithSkillProvider(&PublicStore{API: client}),
)

// 用户每次 Run 显式列 ID
sdk.Run(ctx, prompt, sdk.WithSkills(sdk.Key("code-review"), sdk.Key("security-audit")))
```

`Admin.ListSkills` 返回 `SkillSyncUnsupported`（语义清晰：商店有自己的浏览 UI）。

##### S3：多租户商店（含 tenant required）

```go
type TenantStore struct{ Store *MyStoreClient }

func (p *TenantStore) GetSkills(ctx context.Context, keys []string) (map[string]sdk.Skill, error) {
    id, _ := sdk.CallerIdentityFromContext(ctx)
    fetched, _ := p.Store.BatchGet(ctx, id.TenantID, keys)
    required, _ := p.Store.RequiredFor(ctx, id.TenantID)

    out := make(map[string]sdk.Skill, len(fetched)+len(required))
    for _, s := range fetched  { out[s.Key] = s }
    for _, s := range required { out[s.Key] = s }
    return out, nil
}
```

GetSkills 一个方法解决 fetch + required，宿主自由决定 RPC 合并策略。

##### S4：路径扫描（不需要 Provider）

```go
skills, err := sdk.LocalSkillsFromDir("/opt/skills")
if err != nil { return err }

sdk.New(
    sdk.WithDefaultAgent(...),
    sdk.WithDefaultSkills(sdk.SkillsAsRefs(skills)...),
    // 无 Provider —— inline Skill 直接走 materializer
)
```

**完全不接触 Provider 接口体系** —— inline Skill 的 ref 直接喂给 materializer。

##### S5：混合（本地 + 商店）

```go
localSkills, _ := sdk.LocalSkillsFromDir("/opt/skills")

sdk.New(
    sdk.WithDefaultAgent(...),
    sdk.WithDefaultSkills(sdk.SkillsAsRefs(localSkills)...),  // 本地走 inline
    sdk.WithSkillProvider(remoteStoreProvider),                // 商店 key 走 Provider
)

sdk.Run(ctx, prompt,
    sdk.WithSkills(
        sdk.Key("store-skill-1"),  // 走 Provider.GetSkills
        sdk.Key("store-skill-2"),
    ),
)
```

本地全装、商店按需 —— 自然组合。

#### A1.4 兼容策略（破 v0.4）

v0.5 是 break 版本。允许 break 的依据：v0.4 实际生产基础小、集中迁移成本低、避免长期维护两套 API 心智。

| v0.4 | v0.5 | 迁移代价 |
|---|---|---|
| `SkillProvider.List(ctx, tenantID)` | `SkillProvider.GetSkills(ctx, keys)` | 改方法签名 + 内部从"枚举"转为"按 key 取"（5~30 分钟，看实现复杂度） |
| `WithSkillProvider(SkillProvider)`（v0.4 类型） | `WithSkillProvider(SkillProvider)`（v0.5 类型） | option 名称不变；类型变化触发编译 error 提醒 |
| `WithSkillSet(SkillSet)` | 删除 | `SkillSet` 同时实现 `SkillCatalog`，改为 `WithSkillProvider(set)` |
| `ErrSkillsNotEnumerable` | 删除 | 商店宿主直接不实现 `SkillCatalog`；admin 路径自动 Unsupported |
| `SkillSource.isSkillSource()` 私有 | `SkillSource.SkillSource()` 公开 | 内置类型 SDK 自己改；第三方理论上无（封闭 marker 本来就实现不了） |
| `tenantID string` 入参 | `CallerIdentityFromContext(ctx)` | 实现内 1 行 helper 调用 |

#### A1.5 工作量估计

中：~250 行实现 + 单测 + migration guide。

### A2. `SkillFromArchive` + 内置 archive materializer

#### A2.1 动机

v0.4.0 `SkillSource` 三个内置实现都要求 skill 已经在本地：

- `SkillFromPath`：本地目录
- `SkillFromFS`：`io/fs.FS` 抽象
- `SkillFromInline`：单字符串 SKILL.md

但生产宿主的真实流水线大量是"远端来的压缩包"：

- 远端预签名 URL → HTTP GET → sha256 校验 → unzip → cache
- 商店私有协议 → 鉴权动态签名 → POST body → 拿 zip 字节 → unzip
- 内存里已经持有的 zip 字节 → 直接解压
- 本地的 zip 文件路径 → 解压

每个用 v0.4 + 远端 skill catalogue 的宿主都得自己写一遍：singleflight 去重、content-addressed cache、原子解压、防压缩炸弹、防路径穿越。`agent-registry` 实测约 400 行模板代码，几乎全是 boilerplate。

这套代码：

- 完全 host-neutral（archive 解压策略与宿主业务无关）
- 极易踩坑（singleflight 用错、解压时机错、sha 校验时机错都会 silent corrupt cache；防穿越 / 炸弹漏写直接是 CVE）
- 各宿主重复造，质量参差

是 §7.x "可下沉到 SDK 的标配代码" 的典型。

#### A2.2 改动

##### A2.2.1 新增 `SkillFromArchive` source 类型

```go
type SkillArchiveFormat string

const (
    SkillArchiveAuto  SkillArchiveFormat = ""        // magic-byte 嗅探
    SkillArchiveZip   SkillArchiveFormat = "zip"
    SkillArchiveTar   SkillArchiveFormat = "tar"
    SkillArchiveTarGz SkillArchiveFormat = "tar.gz"
)

// SkillFromArchive sources a skill from an archive stream. The archive
// must contain SKILL.md at its root, or under Subpath when the archive
// wraps the skill in an extra directory layer.
//
// Archive is invoked at materialization time and returns a fresh reader
// of the archive bytes. SDK may invoke it more than once if a cached
// extraction is invalidated; implementations should keep it idempotent.
//
// Format selects the decompressor; an empty value triggers magic-byte
// sniffing. Setting Format explicitly skips sniffing and surfaces format
// mismatches as decompression errors.
//
// Fingerprint controls caching:
//   - non-empty: SDK uses Fingerprint as the cache key; identical
//     fingerprints across runs share the extracted directory under the
//     materializer's cache root
//   - empty: SDK extracts to a run-scoped temp directory and discards
//     it after the run
//
// Hosts that already know the archive's sha256 typically pass it as
// Fingerprint; hosts whose store identifies content by an opaque ID
// (store-id + version) can use that string instead.
type SkillFromArchive struct {
    Archive     func(ctx context.Context) (io.ReadCloser, error)
    Format      SkillArchiveFormat
    Subpath     string
    Fingerprint string
}

func (SkillFromArchive) SkillSource() {}
```

判据 12：`SkillFromArchive` 是"内容载体形态" 抽象，把所有"获取方式"折叠到 `Archive` 这个 reader factory 函数里。

##### A2.2.3 内置 materializer 处理 `SkillFromArchive`

SDK 默认 materializer 在收到 `SkillFromArchive` 时执行：

| 步骤 | 实现要点 |
|---|---|
| 取数据 | 调 `Archive(ctx)` 拿 reader |
| 嗅探格式 | `Format == ""` 时按 magic bytes 判 zip / tar / tar.gz；显式 Format 跳过嗅探 |
| 防压缩炸弹 | 单文件大小上限（默认 64 MiB）、总解压大小上限（默认 256 MiB）、文件数上限（默认 10000）— 都通过 `WithMaxArchive*` 调整 |
| 防路径穿越 | 拒绝包含 `..` 段、绝对路径、出树符号链接的 entry |
| 原子写入 | 解压到 `tmp.<rand>`，完成后 `rename` 到最终路径；中途崩溃下次重做 |
| 缓存 | `Fingerprint` 非空：写到 `<cache_root>/<fingerprint>/`；并发同 fingerprint 用 singleflight 去重；为空：写到 run-scoped 临时目录、Run 结束清理 |

#### A2.3 删除原计划的 `SkillFromURL`

原 v0.5 草案曾有 `SkillFromURL{URL, SHA256, Format, Headers, HTTP}` 类型。**删除**。理由：

- 该语义被 `SkillFromArchive + ArchiveFromURL` 完整覆盖：
  ```go
  // 原 SkillFromURL
  sdk.SkillFromURL{URL: "https://...", SHA256: sha, Format: sdk.SkillArchiveZip,
                   Headers: map[string]string{"Authorization": "Bearer xxx"}}

  // 新写法（行数相当，但抽象层级一致）
  sdk.SkillFromArchive{
      Archive:     sdk.ArchiveFromURL("https://...",
                       sdk.WithArchiveHeader("Authorization", "Bearer xxx")),
      Format:      sdk.SkillArchiveZip,
      Fingerprint: sha,
  }
  ```
- 判据 12：`SkillFromURL` 是按"获取方式"分类的 source，违反"内容载体形态"分类原则；保留它会引诱后续再加 `SkillFromS3` / `SkillFromGRPC` 等

#### A2.4 商店模型重新审视

`SkillFromArchive` 引入后，商店模型的接入路径变成 3 级阶梯：

| 商店类型 | 接入路径 |
|---|---|
| 预签名 URL + zip（最简单） | `SkillFromArchive{Archive: ArchiveFromURL(...), ...}` 一行 |
| 动态鉴权 / POST / 商店私有 RPC，**但产物是 archive** | `SkillFromArchive{Archive: 宿主自定义 closure, ...}`，私有 IO 封在 closure 内 |
| 商店私有协议非 archive（git pack 等） | 自定义 SkillSource（公开 marker） + 自定义 Materializer（chain 默认 materializer） |

绝大多数商店是 case 1 / 2 —— SDK 内置 `SkillFromArchive` 直接覆盖，**不需要自定义 source / materializer**。

宿主商店典型实现：

```go
func (p *StoreProvider) GetSkills(ctx context.Context, keys []string) (map[string]sdk.Skill, error) {
    id, _ := sdk.CallerIdentityFromContext(ctx)
    items, _ := p.Store.BatchGet(ctx, id.TenantID, keys)

    out := make(map[string]sdk.Skill, len(items))
    for _, item := range items {
        out[item.Key] = sdk.Skill{
            Key: item.Key,
            Source: sdk.SkillFromArchive{
                Archive: func(ctx context.Context) (io.ReadCloser, error) {
                    return p.Store.Download(ctx, item.StoreID, item.Version)
                },
                Format:      sdk.SkillArchiveZip,
                Subpath:     item.Subpath,
                Fingerprint: item.StoreID + "@" + item.Version,
            },
        }
    }
    return out, nil
}
```

商店宿主**完全不用自定义 SkillSource、不用自定义 Materializer**，全部走 SDK 内置类型。私有下载逻辑封装在 closure 里，整洁。

#### A2.5 依赖评估（按 §2.4 三条）

实施期间认真调研了 `github.com/mholt/archives v0.1.5`（业界主流的 Go 多格式 archive 库），按 §2.4 三条对照：

| 维度 | stdlib（archive/zip + archive/tar + compress/gzip + crypto/sha256） | mholt/archives v0.1.5 |
|---|---|---|
| **可靠性** | Go core 维护，API 稳定；路径安全 / 防炸弹 / symlink 责任在调用方 | 路径安全责任**也在调用方**（其 `Extract(ctx, in, callback)` 把每个 entry 喂回调，路径检查仍要在回调写）；仅删除了前身 `mholt/archiver` 里有 CVE-2025-3445（zip slip）的 `Unarchive()` 辅助函数，没引入开箱即用的安全 Extract |
| **可持续维护** | Go core | 社区库 v0.1.x 半年内 10 个版本，未稳定；**18 个直接+间接依赖**（brotli / dsnet-compress / klauspost-compress / klauspost-pgzip / rardecode / STARRY-S/zip / sevenzip / xz×2 / minlz / lz4 / lzip / golang.org/x/text / plumbing / windows / golang-lru / afero / go4.org）|
| **可局部化** | 零审计面 | 18 个依赖污染审计面；其中 7z/rar/brotli/zstd/xz/lz4/minlz/S2/lzip 都是 SDK 用不到的格式 |

**关键洞察**：两个方案在 zip slip / 防炸弹 / symlink 处理上的安全责任都在**调用方**。mholt/archives 没有把这层责任接管走——它的 `Extract` 是回调式 API，路径检查仍要写。所以"用第三方库换更多安全保证"是错觉。

**结论**：**不引入 mholt/archives**。继续用 stdlib `archive/zip` + `archive/tar` + `compress/gzip` + `crypto/sha256` + `golang.org/x/sync/singleflight`（已 indirect，提升为 direct 不增加审计面）；自实现路径检查 / 防炸弹 / symlink 拒绝（80~150 行 Go + fuzz 测试），把"安全责任"显式写在 SDK 内部 materializer 路径里，对宿主完全透明。

> 评估结论也作为 §0.2 判据 12 的具体应用：第三方库优先评估"它是否真的把责任接管"，而不是"它有更多 feature"。本评估认为 mholt/archives 只接管了"格式识别"，没接管"安全检查"——SDK 用不到前者（远端 skill 事实标准就是 zip / tar.gz）；后者两边都不接管，所以引入它的收益 = 0，代价 = 18 个依赖。

#### A2.6 工作量估计

中：~350 行实现 + e2e 测试 + 文档（含防炸弹 / 防穿越 fuzz 测试）。

### A3. `RuntimeServiceManager` 增加 `ReleaseByLabels`

#### A3.1 动机

v0.4.0：

```go
type RuntimeServiceManager interface {
    Ensure(ctx, req RuntimeServiceRequest) ([]RuntimeServiceRef, error)
    ReleaseByRun(ctx, runID string) error
}
```

容器化宿主真实场景：进程崩溃 → 重启 → 失去所有内存态 → 只剩 `task_id` 维度的持久化数据。但 SDK 只允许按 `runID` 释放，宿主不得不**绕过 SDK 直接戳 docker daemon** 收拾遗留 runtime service —— 这把整个抽象打穿了。

#### A3.2 改动

```go
type RuntimeServiceManager interface {
    Ensure(ctx context.Context, req RuntimeServiceRequest) ([]RuntimeServiceRef, error)
    ReleaseByRun(ctx context.Context, runID string) error

    // ReleaseByLabels releases all services whose Metadata contains all
    // key-value pairs in labels. Empty labels map releases nothing
    // (caller must explicitly opt-in to broad release with at least one
    // key-value pair).
    ReleaseByLabels(ctx context.Context, labels map[string]string) error
}
```

`RuntimeServiceRequest.Metadata` 在 v0.4.0 已是 label 槽位，无需改 schema；只是把"按 label 释放"提升为接口要求。

#### A3.3 为什么不加 `Reconcile(aliveRunIDs)`

最初草案包含 `Reconcile(ctx, aliveRunIDs []string) error`。**砍掉**。理由：

1. **宿主重启后没有 `aliveRunIDs`**。`RunID` 是 SDK 进程内分配的，进程一挂就丢；宿主数据库里只有 `task_id`（task : run = 1 : N）。
2. **隐含"列出所有资源"能力**。当前接口都是命令式（host 知道 desired state，SDK 执行）；`Reconcile` 强制实现枚举所有 service，给了宿主一种"SDK 帮我管 lifecycle"的错觉，违反 §1 / §8。
3. **重复**。宿主真实需要的清理流程，用 `ReleaseByLabels` 完全等价表达：
   ```go
   for _, taskID := range deadTaskIDs {
       _ = mgr.ReleaseByLabels(ctx, map[string]string{"task_id": taskID})
   }
   ```

如果未来 `ReleaseByLabels` 在大规模场景下证明不够（比如真的需要"列出再过滤"），到时候单独讨论 `ListByLabels` 这个**只读**接口，而不是 `Reconcile` 这个有 mutating 副作用的接口。

#### A3.4 兼容策略

接口扩展是 break。SDK internal 提供 mixin：

```go
package runtimeservice

// NoopReleaseByLabels is a drop-in mixin for v0.4.0 implementations.
// Hosts that don't yet need label-based release embed it and keep
// existing functionality intact.
type NoopReleaseByLabels struct{}

func (NoopReleaseByLabels) ReleaseByLabels(_ context.Context, _ map[string]string) error {
    return nil
}
```

宿主 1 行 embedding 即可：

```go
type myMgr struct {
    runtimeservice.NoopReleaseByLabels
    // ... existing fields ...
}
```

小：~50 行（核心类型扩展 + mixin + 测试）。

### A4. 公共错误集中归档 + 矩阵表 + 极简谓词

#### A4.1 动机

v0.4.0 共 ~13 个 public error 散落 5 个文件：`errors.go`、`skill_types.go`、`session_types.go`、`run_types.go`、`decision_types.go`。宿主写错误处理要盯多处，新人 PR 经常漏一两个 `errors.Is`。

错误码与"宿主推荐响应"也没集中文档：宿主拿到 `ErrDecisionRequestExpired` 应该 ack 200 还是 409？拿到 `ErrSkillKeyConflict` 应该 4xx 还是 5xx？现在只能去看源码注释。

#### A4.2 改动

1. 新增 `errors_public.go`：所有 `Err*` 集中归档为一个 `var ( ... )` 块，附 doc comment 矩阵表
2. **只保留单 sentinel 谓词**，仅限有"真行为分支价值"的少数几个：
   ```go
   func IsRunEnded(err error) bool             // ErrRunEnded
   func IsDecisionExpired(err error) bool      // ErrDecisionRequestExpired
   func IsSessionBusy(err error) bool          // ErrSessionBusy / *SessionBusyError
   func IsSessionIncompatible(err error) bool  // ErrSessionIncompatible / *SessionIncompatibleError
   func IsSkillKeyConflict(err error) bool     // ErrSkillKeyConflict / *SkillKeyConflictError
   ```
3. 新增 `docs/public-errors.md`：完整列表 + 触发场景 + 宿主推荐响应（HTTP code / 是否记日志 / 是否告警）

#### A4.3 为什么不做聚合谓词

最初草案有 `IsExpired(err)`（合并 `ErrDecisionRequestExpired` + `ErrRunEnded`）、`IsConflict(err)`（合并 `ErrSkillKeyConflict` + `ErrDuplicateAgent` + …）等。**全部砍掉**。理由：

- **聚合是单向不可逆的**：宿主写了 `if IsExpired(err)` 之后，**永远** 不能在不破坏行为的前提下让 `ErrRunEnded` 分裂出 `ErrRunEndedNormally / ErrRunEndedAborted` —— 哪怕新行为对宿主无害，谓词的语义已经漂了
- **跨 sentinel 的"语义相近"是 SDK 作者的视角，不是宿主的视角**：宿主拿到 `ErrSkillKeyConflict` 和 `ErrDuplicateAgent` 时的处理路径完全不同（前者是"清理 catalogue"、后者是"修构造时配置"），合并成 `IsConflict` 反而误导
- `errors.Is(err, ErrXxx)` 已够用；多写谓词的收益只在"少打几个字"上，每多一个谓词就多一份**永久维护合同**

保留下来的 5 个谓词都满足两个条件：

1. 对应的 error 已是 typed error，谓词只是 typed-error 的语法糖
2. 宿主存在明确的行为分支

其它一律走 `errors.Is`。

#### A4.4 兼容策略

纯新增，无 break。原有 `Err*` 变量位置不变（`errors.go` 等保留 `var X = errs_public.X` 重定向；`errors_public.go` 是 source of truth）。

小：~120 行 + 文档。

##### B1.2.1 新增 `PendingDecisions` 纯函数 helper

// This is the SDK-recommended path for hosts that need a "pending
// decision list" view: derive on demand from existing history rather
// than persisting a separate pending dimension. The recorder remains
// the single source of truth.
//

零状态、零 IO、零新存储维度。`Recorder` / `Backend` 接口完全不动。

##### B1.2.2 doc.go 文档化 `sessionKey` 选取（带 trade-off）

新增约 50 行注释：

```go
// sessionKey is intentionally a neutral aggregation key. There are two
// canonical patterns; pick one and keep it stable per logical thread
// you want to read back:
//
//  1) Audit style (recommended starting point): sessionKey = RunID
//     - one record stream per run, immutable after the run ends
//     - multi-pod hosts: routing-agnostic; any pod can append
//     - downside: cannot accumulate cross-run history of the same
//       logical conversation; the host correlates RunIDs externally
//
//  2) Conversation style: sessionKey = ThreadID
//     - history accumulates across multiple SDK SessionIDs (forks /
//       continues) under the same UI thread
//     - downside: multi-pod hosts MUST route stickily by sessionKey,
//       otherwise HostSeq across pods will collide and the cursor
//       protocol breaks
//
// Single-process / single-pod hosts can pick either. Multi-pod hosts
// should default to (1) and only graduate to (2) once they have a
// sticky-routing layer (or plug a coordinator-aware Backend such as
// one using Redis INCR).
```

##### B1.2.3 `examples/streaming-chat-copilotkit` 加 fan-out 示例

##### B1.2.4 增量 `PendingTracker` —— 避免长会话 O(n²)

宿主侧"每个 HITL 事件来了 → 重新 derive 全部 pending → 推给 UI"是真实存在的使用模式。如果只暴露 `PendingDecisions(records)` 这一个一次性快照 API，宿主自然会在循环里调它，触发 O(n²) per-session：

```go
// ❌ 长会话（chatbot 上千条消息）下退化到 O(n²)
for rec := range incomingRecords {
    history = append(history, rec)
    pending := sessionrecorder.PendingDecisions(history) // O(n) per call
    broadcast(pending)
}
```

新增 `PendingTracker` 把状态机包好，提供 O(1) per Apply：

```go
// ✓ Tracker：增量式，O(1) per Apply
tracker := sessionrecorder.NewPendingTracker()
for rec := range incomingRecords {
    tracker.Apply(rec) // O(1) amortized; 非 HITL record 直接跳过
    if isHITL(rec.Payload.Kind) {
        broadcast(tracker.Snapshot()) // O(pending count), 通常很小
    }
}
```

API 表面：

```go
type PendingTracker struct{ ... }
func NewPendingTracker() *PendingTracker
func (t *PendingTracker) Apply(rec Record)
func (t *PendingTracker) Snapshot() []agentadaptor.DecisionRequest
func (t *PendingTracker) Reset()
```

定位：

- **`PendingDecisions(records)`**：一次性快照，适合 admin dump / REST handler 一问一答
- **`PendingTracker`**：长会话循环、UI 实时推送、需要并发安全（一写多读）

`PendingDecisions` 内部基于 `PendingTracker` 实现（`NewPendingTracker` + 全 Apply + Snapshot），单次调用复杂度等价；区别只在循环模式下：

| 场景 | PendingDecisions | PendingTracker | 实测（2000 events）|
|---|---|---|---|
| 单次快照（n=10000） | O(n) | O(n) | 两者基本相等（~2ms） |
| 长会话每事件重 derive | **O(n²)** | **O(n)** | **40ms vs 348ms（8.6x）**；10K events 差距约 80x |

并发：`PendingTracker` 全 API 线程安全，典型一写多读模式下 `-race` 干净。

判据归属：
- §0.2 判据 1（数据流正交）：Tracker 与 PendingDecisions 处理同一数据流，但"快照式 vs 增量式"是计算模式分裂，类似 `io.Reader` / `bufio.Reader` 的关系，合法
- §0.2 判据 7.x（标配代码下沉）：手写 80 行带并发的状态机是宿主标配代码，沉淀进 SDK 一次值得

#### B1.3 为什么不在 sessionrecorder 加 pending 存储维度

最初草案是给 `Recorder` 加 `AddPending / RemovePending / PendingRequests`，给 `Backend` 加 `LoadPending / SavePending`。**全部砍掉**。理由：

1. **`pkg/hosttools/sessionrecorder/doc.go` 已明确写**:
   > "pending DecisionRequest tracking — that's per-run runtime state that evaporates when the RunHandle goes away"

   这是 SDK 已经做出的边界判断。"5 件里 4 件已经做了，所以加第 5 件" 是凑齐逻辑，不是必须做逻辑。

2. **HITL pending 持久化不是 host-neutral 的**。进程一挂，pending 持久化也无法自动 resume（§7.4 自承认）。pending 持久化的真实价值是"宿主重启后能告诉 UI：你之前的 run 卡在等审批" —— 纯 UI 状态展示，不是执行恢复。

3. **同样能力可从 history derive**。30 行代码，零新存储。

4. **持久化 pending 必有"双写不一致"风险**。pending 是 history 的派生视图；让它独立持久化等于强制每次 resolved 事件做"一次写 history、一次写 pending"的双写，崩溃顺序错了就脏数据。derive 路径根本没有这个风险。

#### B1.4 为什么不引入 `Sink` / `Pump` 抽象

砍掉理由：

- fan-out 不是 sessionrecorder 的职责。它是通用 channel 多路分发，把它装进 sessionrecorder 等于绑定了"fan-out 抽象"和"recorder 实现"的版本演进
- 文档原本说能减少宿主 80 行代码。**这 80 行是宿主应当自己写的"业务接缝"**：每路 sink 的错误处理、buffer 大小、是否 drop、是否带超时，完全是宿主业务决定的
- `Pump` 里隐含的 "Sink errors are logged but do not abort the pump" 一旦写进 SDK 就成合同，宿主想改要么 fork 要么绕过去
- 在 hosttools 包内造小框架是越界 —— `pkg/hosttools/*` 的定位是"宿主可选用的工具集合"，不是"宿主自带 mini-runtime"

#### B1.5 兼容策略

- `Recorder` / `Backend` 接口完全不动，0 break
- 内置 `MemoryBackend` / `JSONLBackend` 行为不变
- 第三方 backend 不需要任何调整

### C2. `SessionStore` doc comment 强化 + `usage-guide.md` 命名陷阱段

#### C2.1 动机

经过 §C1 澄清后已明确：宿主侧的 thread / conversation 维度持久化跟 SDK 的 `SessionStore` 是**两个 ontology 维度**：

- `SessionStore` 按 `SessionID` 索引，存的是 driver state metadata（resume tokens / fingerprint / lease）
- thread 维度按 `ThreadID` 聚合，存的是用户面 stream payload 历史（pending 由其 derive）
- 两者基数：1 ThreadID : N SessionID（fork / start_new 时 SessionID 会换，ThreadID 不换）

历史上有过把 `SessionStore` 改名为 `DriverSessionStore` 的提案，**否决**：

- "Session" 在 SDK 自己的 ontology 里就是合适的术语
- 改名暗示"还有别的 SessionStore"，反而模糊概念
- 撞名根源是宿主侧命名不规范，不是 SDK 的责任
- 改名是 break，文档化是零成本

正确做法是**给 godoc 加权威边界说明**，挡掉宿主把 ThreadHistory 误塞进来的冲动。

#### C2.2 改动

##### C2.2.1 `session_types.go` 强化 doc comment

```go
// SessionStore persists SDK-level session state for resume-capable adapters.
//
// "Session" here is the SDK's session ontology (see AGENTS.md §6):
//   - resume tokens, compatibility fingerprints, lease coordination
//   - mode-driven lifecycle (continue_or_start / start_new / fork / ...)
//   - indexed by SessionID; (Namespace, Key) is a secondary index
//
// SessionStore is NOT the right place for:
//   - host-facing chat / thread / conversation history payloads
//     → use pkg/hosttools/sessionrecorder with sessionKey = ThreadID
//       (or sessionKey = RunID for audit-style recording)
//   - HITL pending requests
//     → derive on demand via sessionrecorder.PendingDecisions(records);
//       do not persist a separate pending dimension
//   - "the conversation a user sees in a chat UI"
//     → host concern; the SDK exposes no equivalent abstraction
//
// Hosts that need any of the above should compose pkg/hosttools/sessionrecorder
// (and their own task store), not implement SessionStore.
type SessionStore interface { ... }
```

##### C2.2.2 `usage-guide.md` 加命名陷阱段

新增 "宿主集成 — 命名陷阱" 段，列举 5 种典型错误：

1. 把宿主自己的 ThreadHistoryStore 叫 `SessionStore`（与 SDK 撞名）
2. 把 `RunID` 当 `SessionID` 使用（生命周期错配，fork / continue 立即出问题）
3. 把 `sessionrecorder.Recorder` 的 `sessionKey` 当 `SessionID` 使用（无法跨 fork 累积同 thread 历史）
4. 在宿主的 outbound API 里把 `task_id` 和 `thread_id` 混用（task : thread 是 1:N，不是同一维度）
5. 给 `SessionStore` 加 `SaveHistory / LoadHistory` 方法（边界违反；走 `sessionrecorder`）

每条给"应该怎么写"的修正示例。

#### C2.3 工作量估计

小：~60 行注释 + ~120 行文档。

## 7. 风险与已知 trade-off

### 7.1 A1 的 break 集中在 `SkillProvider` 实现层

`SkillProvider.List(ctx, tenantID)` → `SkillProvider.GetSkills(ctx, keys)` 是真 break，每个自定义 `SkillProvider` 都得改方法签名 + 内部从"枚举"转"按 key 取"。

**判断**：v0.4 实际生产基础小，集中迁移成本可控。migration guide 给 5 种场景（静态 / 公共商店 / 多租户商店 / 路径扫描 / 混合）的完整 cookbook，每种 < 30 行示例。

### 7.2 A2 archive materializer 安全性

`SkillFromArchive` 的内置实现要正确处理：压缩炸弹、路径穿越、符号链接、文件类型（仅常规文件 + 目录）、UTF-8 文件名。任何一处漏写就是 CVE。

**判断**：通过 fuzz 测试（zip / tar / tar.gz 的恶意构造）+ 经典攻击向量集（zip slip、zip64 size lying、tar header truncation 等）覆盖；评估期内（PR3）邀请安全 reviewer 走查一轮。

### 7.3 A3 仍是 break

`RuntimeServiceManager.ReleaseByLabels` 让现存自定义实现无法直接编译。`NoopReleaseByLabels` mixin 把代价压到 1 行。

**判断**：v0.5.0 是合适的承担时机，且这个 break 直接挡掉一个误用入口（绕过 SDK 戳 docker daemon）。

### 7.4 B1 让 pending 列表 derive 而非持久化 → 长会话循环模式下的 O(n²)

`PendingDecisions(records)` 是单次 O(n) 线性扫描。**真实风险**是宿主在长会话里每个新 record 都调它（典型 chatbot 上千条消息），整体退化到 O(n²)。

**Mitigation（v0.5 已落地）**：`PendingTracker` 增量类型把状态机包好（O(1) per Apply），见 §B1.2.4。

- 一次性查询 / admin dump：用 `PendingDecisions(records)`（O(n) 单次）
- 长会话循环 / UI 实时推送：用 `PendingTracker`（O(1) per Apply + O(pending) per Snapshot）
- 不持久化 pending 反而消除了"pending 与 history 不一致"这类难以排查的脏数据问题
- 实测：2000 events 长会话循环模式下，`PendingTracker` (40ms) vs 反复调 `PendingDecisions` (348ms) 差 8.6x；10K events 差距约 80x

### 7.5 v0.5.0 不解决 RunHandle 跨进程恢复

容器重启后，进程内 `RunHandle` 全部失效，仍由宿主自己处理"用户在 Web IDE 看到上一次 run 的最后状态"这件事。

**判断**：这是 SDK ontology 边界（RunHandle 是进程内对象）；如果跨进程恢复将彻底重设计 Run 模型，超出 v0.5.0 范围。当前已有 `sessionrecorder` 让宿主重放历史 + `PendingDecisions` derive pending 列表，足够 UI 层"刷新到最新已知状态"。

### 7.6 不内置 fan-out 抽象 → 三路分发在每个宿主里都会被重写一遍

每个宿主仍需写自己的 `for payload := range ch { ... }`。

**判断**：这恰恰是想要的结果。fan-out 的错误处理 / buffer / drop 策略**必须**在宿主侧定义；SDK 给一个抽象只会让宿主以为"我不用想了"，结果踩坑后又要绕开。

### 7.7 `AgentIdentity` 杂物间问题被 ctx + helper 隔离，但未被根治

`AgentIdentity` 仍混合 identity（ID/Name）与 scope（TenantID/ProfileID）两类语义。v0.5 通过 `CallerIdentityFromContext` 把它隔离在 hook 实现细节里，不污染 SkillProvider 接口签名 —— 但杂物间本身仍在。

**判断**：留笔记给 v0.6 — 届时统一拆为 `Identity{ID, Name}` + `CallScope{TenantID, ProfileID}`，影响 binding / Run / Session / RuntimeService 整条透传链。`SkillProvider` 接口签名届时无需变化（helper 返回类型可以平滑升级）。
